# Техническая основа статического MVP

## Статус

- Статус: согласовано; зависимости ещё не установлены.
- Дата: 2026-07-26.
- Цель: выбрать минимальную основу для статического одностраничного сайта, локальной приёмки и последующего деплоя в nginx.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Чистые HTML, CSS и JavaScript | Нет production-зависимостей, минимальная поверхность атаки | Ручная сборка секций и работы с изображениями, неудобное расширение архивом мероприятий | Не выбирать |
| Vite + TypeScript без UI-фреймворка | Быстрый dev-сервер, простая сборка в `dist/` | Не даёт шаблонизацию и статическую генерацию страниц сам по себе; придётся вручную строить DOM или добавлять ещё один инструмент | Запасной вариант |
| Astro + TypeScript | Статическая генерация по умолчанию, компонентная вёрстка без обязательного клиентского JavaScript, встроенная работа с изображениями, простой `dist/` | Одна production-зависимость и дополнительный синтаксис `.astro` | Рекомендуется |
| React/Next.js или другой полнофункциональный UI-фреймворк | Большая экосистема и развитая интерактивность | Избыточная клиентская и серверная сложность для одной информационной страницы | Не выбирать |

## Рекомендация

Использовать:

- Astro в статическом режиме;
- TypeScript со строгими проверками;
- npm;
- обычные Astro-компоненты без React, Preact, Vue или Svelte;
- обычный CSS с custom properties без Tailwind и CSS-in-JS;
- минимальный нативный JavaScript только для поведения навигации, фиксированного CTA и осмысленных анимаций;
- локальные изображения в `src/assets/images/` через встроенные компоненты Astro `<Image />` и `<Picture />`;
- выходную папку `dist/` для локальной проверки и дальнейшей публикации nginx.

Текущая локальная среда подходит: Node.js `v24.16.0`, npm `11.13.0`. Astro требует Node.js `v22.12.0` или выше и не поддерживает нечётные версии Node.js.

## Почему это подходит проекту

- Сайт остаётся статическим и не требует приложения на сервере.
- Основная страница генерируется в готовый HTML, поэтому базовое содержание не зависит от выполнения JavaScript в браузере.
- Фотографии можно оптимизировать во время сборки и выдавать адаптивные размеры и форматы.
- Компоненты позволяют поддерживать выразительную длинную страницу без копирования разметки между секциями.
- В будущем можно добавить страницы прошедших мероприятий, не меняя способ деплоя.
- Результат сборки совместим с отдельным каталогом nginx на существующем сервере.

## Контент

Для первой версии не использовать Astro Content Collections: сайт содержит одно текущее мероприятие и небольшое число страниц. Вместо этого создать один типизированный файл:

```text
src/data/event.ts
```

Файл хранит:

- метаданные и SEO;
- название, даты, город и возрастное ограничение;
- ссылки регистрации;
- связанные этапы проекта;
- описание лаборатории;
- аудиторию и результаты участия;
- сведения о челлендж-джеме;
- формат и программу;
- тарифы;
- ведущих;
- галерею;
- партнёров и контакты.

Изображения импортируются в этом же файле из `src/assets/images/`, чтобы Astro мог обработать их при сборке.

Когда появится несколько прошедших мероприятий, возможны два шага расширения:

1. Перейти к массиву типизированных событий в `src/data/events.ts`.
2. При росте архива перенести события в Astro Content Collections с общей схемой и статической генерацией страниц.

CMS в MVP не подключается.

## Предлагаемая структура

```text
src/
  assets/
    images/
  components/
    sections/
  data/
    event.ts
  layouts/
    BaseLayout.astro
  pages/
    index.astro
  styles/
    global.css
public/
docs/
content/
```

Не создавать универсальную библиотеку компонентов заранее. Отдельный компонент оправдан, если он соответствует самостоятельному смысловому блоку или повторяется.

## Локальная разработка и проверка

После подтверждения стека должны быть доступны команды:

```text
npm run dev
npm run check
npm run build
npm run preview
```

Порядок приёмки:

1. Рабочая проверка через локальный dev-сервер.
2. Статическая проверка типов и Astro.
3. Production-сборка в `dist/`.
4. Локальный preview именно содержимого `dist/`.
5. Визуальная проверка мобильной и десктопной версий.
6. Явное согласование пользователя.
7. Только после этого — домен и деплой.

## Интерактивность и движение

На первом этапе не добавлять библиотеку анимаций. Использовать CSS и небольшой нативный JavaScript:

- сдержанное появление композиции первого экрана;
- последовательное раскрытие трёх этапов проекта при прокрутке;
- понятные hover/focus-переходы CTA;
- обязательная поддержка `prefers-reduced-motion`.

Если в ходе прототипирования станет ясно, что нативных средств недостаточно для конкретного согласованного эффекта, новая зависимость обсуждается отдельно.

## Бюджет производительности

Приоритет — быстрая первая загрузка и плавный скролл на мобильных устройствах.

Обязательные ограничения для MVP:

- не подключать клиентский UI-фреймворк;
- целевой объём собственного клиентского JavaScript — не более 30 КБ gzip;
- не использовать постоянные тяжёлые обработчики события `scroll`;
- для появления секций использовать CSS и `IntersectionObserver`;
- анимировать преимущественно `transform` и `opacity`;
- отключать необязательные scroll-эффекты на мобильных устройствах;
- учитывать `prefers-reduced-motion`;
- не использовать фоновое видео в первом MVP;
- хранить локальные изображения в `src/assets/images/` и генерировать адаптивные варианты;
- загружать изображения ниже первого экрана лениво;
- для первого экрана использовать отдельный оптимизированный мобильный размер;
- самостоятельно размещать и подготавливать только действительно используемые начертания шрифтов.

Цели проверки production-сборки:

- Lighthouse Mobile Performance: не ниже 90 в медиане трёх локальных запусков;
- LCP: не более 2,5 секунды;
- CLS: не более 0,1;
- INP после публикации и появления полевых данных: не более 200 мс;
- отсутствие заметных рывков прокрутки на мобильной ширине при ручной проверке;
- отсутствие горизонтального переполнения и скачков макета при загрузке изображений.

Локальная лабораторная проверка не может полноценно измерить INP без реальных взаимодействий, поэтому до появления полевых данных дополнительно контролируются объём JavaScript, длинные задачи главного потока и Total Blocking Time.
